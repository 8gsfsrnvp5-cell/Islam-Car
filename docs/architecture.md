# Архитектура Islamic Car

## Состав системы

```
                ┌──────────────────────┐        ┌──────────────────────┐
  покупатель ──▶│ apps/client (Next.js)│        │ apps/admin (Next.js) │◀── сотрудники
                │  :3000  /api/* proxy │        │  :3001  /api/* proxy │
                └──────────┬───────────┘        └──────────┬───────────┘
                           │  cookie ic_client_session      │  cookie ic_admin_session
                           ▼                                ▼
                ┌──────────────────────────────────────────────────────┐
                │            services/api (FastAPI, :8000)             │
                │  /api/public  /api/auth  /api/client  /api/admin     │
                │  права проверяются только на сервере                 │
                └──────────┬──────────────────────────────┬────────────┘
                           ▼                              ▼
                   PostgreSQL (единая база)        storage/ (фото, файлы)
```

- **Один сервер, одна база.** Оба веб-приложения не имеют собственной базы и не ходят в неё напрямую. Всё идёт через API, поэтому расчёты синхронизированы автоматически: остаток долга, который видит покупатель, и остаток в админке — это один и тот же расчёт на сервере.
- **Прокси `/api/*`.** Каждое Next.js-приложение проксирует `/api/*` на сервер. Cookie сессии остаются first-party, CORS не нужен.
- **Две «зоны» авторизации.** Сотрудники и покупатели логинятся в разные зоны (`admin` / `client`) с разными cookie. Токен клиентской зоны не принимается админскими маршрутами и наоборот.

## Сервер (services/api)

| Слой | Где | Что делает |
|---|---|---|
| Маршруты | `app/routers/` | `public` (каталог, заявки, статус заявки), `auth`, `client` (личный кабинет), `admin/*` |
| Права | `app/security.py`, `app/permissions.py` | сессии в БД, роли `owner/admin/manager/accountant/client`, карта разрешений |
| Бизнес-логика | `app/services/` | `schedule.py` — график, `ledger.py` — распределение платежей и остаток, `contracts.py` — проверки и подписание, `dashboard.py` — показатели |
| Данные | `app/models.py` | SQLAlchemy 2, миграции Alembic в `alembic/versions` |
| Журнал | `app/services/audit.py` | неизменяемый журнал действий сотрудников |

### Деньги

Все суммы хранятся целыми **копейками** (`BIGINT`). Никаких `float`. Ежемесячный платёж округляется до целого рубля вниз, остаток округления переносится в последний платёж — сумма графика всегда точно равна задолженности.

### Платежи и остаток долга

- Платёж учитывается **только** после подтверждения сотрудником с указанием даты поступления и банковского/кассового документа (`payments.status = confirmed`).
- Кнопка покупателя «Я оплатил» создаёт `payment_reports` — это заявление, на остаток оно не влияет.
- Распределение платежей по графику не хранится, а **вычисляется** (FIFO: сначала первоначальный взнос, затем самые ранние платежи). Поэтому после сторнирования ошибочного платежа всё пересчитывается само и не бывает рассинхронизации.
- Платёж нельзя удалить. Ошибочный платёж сторнируется с причиной (`status = reversed`), исходная запись остаётся. Исправленный платёж ссылается на сторнированный (`corrects_payment_id`).
- Просрочка увеличивает только счётчик просроченной суммы. Проценты, пени и штрафы за просрочку **не начисляются** — это зафиксировано в договоре (`no_interest_on_delay`) и в коде расчёта.

### Мурабаха: защитные правила на сервере

- Договор можно подписать только для автомобиля в статусе собственности `owned` с VIN и закупочной стоимостью (продавец должен владеть товаром до продажи).
- Окончательная цена, наценка и график фиксируются при подписании; после подписания финансовые условия через API не меняются (изменения — только дополнительным соглашением, версия 2).
- Закупочная стоимость не попадает в публичный каталог. Покупателю она раскрывается в его договоре, если включено раскрытие (по умолчанию включено для мурабахи).
- Автомобиль `purchasing` (в процессе закупки) показывается в каталоге с явной пометкой и не может быть продан до перехода в собственность.

## Клиентское приложение (apps/client)

Каталог (серверный рендеринг для поисковиков), карточка автомобиля с заявкой, заказ автомобиля, которого нет в каталоге, страница статуса заявки по секретной ссылке, вход, активация доступа, личный кабинет (договор, график, платежи, выписка CSV, «Я оплатил», обращения, уведомления, реквизиты).

## Административное приложение (apps/admin)

15 окон из ТЗ — у каждого свой маршрут. Окна, которые относятся к версиям 2–4, открываются, но явно помечены «не реализовано в этой версии» и не показывают выдуманных данных.

## Фоновые сервисы и агенты

- `services/workers` — версия 2 (напоминания, Celery + Redis). В версии 1 уведомления внутренние (в админке и личном кабинете), создаются синхронно сервером.
- `services/agents` — версия 3. Агенты будут работать через те же сервисные функции и права, что и API; расчёты — только детерминированным кодом, ИИ не вычисляет суммы, ставки и сроки.

## Хранение файлов

Фото автомобилей — в каталоге `storage/` (вне git), путь задаётся `STORAGE_DIR`. Публично отдаются только фото опубликованных автомобилей.
